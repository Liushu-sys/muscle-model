# 轮廓修缮说明：去细丝 / 平滑锯齿

> 一次性的形状修缮，改了 `assets/body_paths.json` 里 16 组肌肉的轮廓。
> 原始数据完整保留在 `assets/body_paths.raw.json`，随时可回滚对照。
> 修缮脚本：`tools/fix_body_paths.py`（可重复跑，可只跑指定肌肉）。

---

## 一、问题长什么样

正面髋内收肌（`hip_adductors`）在大腿内侧靠膝的位置，会拖出一条几乎贴着腿走、
来回折返的"细丝"。填充时看不出来，可一旦描边（前端是 fill + stroke 一起画的），
它就是一撮歪扭的锯齿毛刺。

同类的还有胫骨前肌、前臂屈肌群、腹外斜肌等——都是**末端**多出一条零点几单位宽、
几十个单位长的窄带。

## 二、为什么会这样

`body_paths.json` 是从 3D 模型（`anatomy.glb`）投影 + 描边自动提取的。在投影过程
中，肌块末端贴近骨面/相邻肌块的那一小片会被压成极窄的条带；顶点密度也跟着暴涨
（髋内收肌 233 个顶点里，49 个挤在膝部 40 单位内）。这不是"画错了肌肉"，是提取
噪声，不影响解剖表达的语义，但影响观感。

## 三、怎么判断哪块该修

`tools/fix_body_paths.py --report` 会给 49 组肌肉打分，判据是两个：

| 指标 | 含义 | 为什么这么定 |
|---|---|---|
| 局部厚度 | 某顶点到「沿路径弧长 ≥ 3 单位之外」的最近顶点的距离 | 肌肉末端本来就会收窄成尖角，那是正常的；要看的是"又细**又长**" |
| 细丝弧长 | 厚度 < 1.5 单位的连续段有多长（弧长，不是点数） | 把"正常收窄（几个点）"和"细丝（几十个点连续贴一起）"分开 |

分级：细丝弧长 ≥ 6 单位 → 红档（必修）；≥ 3 单位或顶点过密 → 黄档（顺手修）；
其余 → 绿档（**一个像素都不动**）。

> 踩过的坑：一开始按"顶点序号"排除邻居来量厚度，结果髋内收肌被漏判成绿档——
> 因为细丝是高频折返，走两三个点就折到对面去了，那些"对面点"恰好被序号过滤掉，
> 厚度被算成了到肌肉主体的距离。改成按**弧长**过滤才对。这也是为什么一定要用
> 弧长判据的原因。

## 四、怎么修

栅格形态学重建，只对红/黄档做：

```
栅格化（4x 超采样） → 开运算（腐蚀 r 再膨胀 r） → 轮廓跟踪 → 统一绕向
→ Douglas-Peucker 简化 → Chaikin 平滑
```

- **开运算**只吃细结构：宽度小于 2r 的细丝被削掉，宽 8~17 单位的正常肌块几乎不变。
  - 红档 r = 3（去掉 < 1.5 单位宽的细丝）
  - 黄档 r = 2（去掉 < 1.0 单位宽的细丝，基本等于只做平滑）
- **等量膨胀**（腐蚀 r 再膨胀 r）保证面积忠实，最终几何面积变化在 -8.8% ~ -0.0%。
- **碎屑过滤**：开运算会把细丝末端的膨大切成独立小块（前臂屈肌群被切出 9 个不到主体
  1% 的碎点），面积低于主体 2% 且低于 3 平方单位的一律丢掉；而胫骨前肌那种占主体
  16% 的下段是真结构，会保留。
- **平滑**：DP(0.30) → Chaikin ×2 → DP(0.22)，顶点数普遍减半（如髋内收肌 233 → 131）。

### 为什么不干脆把半径开大

试过 r = 4/5/6：肌肉被削瘦、打散成 3~4 块，细丝反而又冒出来（碎片自身也算细长）。
**r = 3 是拐点**——足够吃掉细丝，又不伤主体。

## 六、怎么复现 / 再修

```bash
python3 tools/fix_body_paths.py --report          # 诊断，不改文件（npm run check:paths）
python3 tools/fix_body_paths.py --apply           # 修缮并写回（自动备份原件）
python3 tools/fix_body_paths.py --apply --ids hip_adductors   # 只修一组
python3 tools/fix_body_paths.py --apply --dry     # 演练，不落盘
python3 tools/fix_body_paths.py --restore         # 全量退回原件（npm run fix:restore）
python3 tools/build_fix_compare.py                # 出前后对比图（npm run fix:compare）
```

> **可重复跑**：修缮的输入一律取原件 `body_paths.raw.json`（不是当前文件），所以
> 同一条命令跑多少次，结果都完全一样——不会把已经修好的组再过一轮开运算。
> 想在当前结果上继续动手时才加 `--inplace`。`--what muscles` / `--what body`
> 只替换自己那一部分，互不干扰，先后顺序随意。

改完 `body_paths.json` 之后，下游要跟着刷三步：

```bash
python3 tools/gen_body_sides.py       # 左右分离数据（会同步到 src/assets/）
python3 tools/build_preview_html.py   # 预览页里的矢量路径
python3 tools/build_body_preview.py   # 静态样张 PNG
```

> 注：`tools/extract_body_svg.py`（`npm run gen:preview`）是从 25MB 的 `anatomy.glb`
> 重新投影，需要自备模型文件；只修轮廓的话用不上它，用 `build_preview_html.py`
> 刷新预览页就够了。两者产的是同一个文件，不要同时跑。

改完记得跑一遍全套校验：`npm run check:data && npm run check`。

## 七、人体外形线（body）：竖直长边上的来回摆

上面六节修的是**肌肉**。人体**外形线**（`front.body` / `back.body`，也就是前端
`outline` 字段渲染的那条轮廓）是另一份数据，有另一种毛病。

### 现象

正面腿部膝内侧的轮廓，在 15 单位高度里 x 来回摆了三次（111 → 106.7 → 110.8 → 107.2），
幅度 3~4 单位，还夹着几个几乎水平挤在一起的点。看着就是"曲里拐弯"。

### 为什么肌肉那套用不了

两个方法都试过，都不行：

| 方法 | 结果 |
|---|---|
| 栅格开运算（肌肉那套） | 会把手指、脚趾一起削掉——body 含这些细节，不能动大手术 |
| 中值滤波 / 高斯平滑 / 弦高简化 | 手指和膝部的**尺度太接近**：能治膝部的强度（±5 点中值、σ=6 高斯）会把手指标磨成圆块；保住手指的强度又治不干净膝部。弦高简化更糟——只会把摆动压成硬折角，更难看 |

### 判据：跨弦 + 竖直

定点处理，只动同时满足两条的点：

| 条件 | 含义 | 实测 |
|---|---|---|
| ① 跨弦摆动 | 窗口（弧长 ±10）内的轮廓跑到端点连线的**两侧**。直线段和正常凸起都只在一侧 | 腿膝内侧 ✓ |
| ② 竖直长边 | 窗口内 `|Δy| / 弧长 ≥ 0.65` | 腿 **0.67~0.85**；手指缝/耳后 **0.01~0.38** |

② 是分开"腿"和"手"的钥匙：手指缝也满足 ①（那是指缝的形状，方向杂乱），但只有
腿这种"上下走向的长边被采样成锯齿"才满足 ②。实测命中 21 点（front）/ 24 点（back），
全部落在腿部膝内侧，手指一根没碰。

处理方式：命中的点前后各扩 3 点，用 σ=7 的高斯在弧长邻域内做定向平滑，迭代 3 轮；
其余点一个不动。

### 结果

| 视图 | 点数 | 移动点 | 最大位移 | 包围盒 |
|---|---|---|---|---|
| front body | 569 | 65 | 4.42 单位 | y 5~456 不变 |
| back body | 566 | 92 | 5.74 单位 | y 5~456 不变 |

膝内侧从"锯齿"变成顺滑曲线，手指、头部、四肢比例都没变。安全阈值：单点位移超过
8 单位就跳过并报警（防止把轮廓拉飞）。

```bash
python3 tools/fix_body_paths.py --report --what body    # 先看摆动段在哪
python3 tools/fix_body_paths.py --apply  --what body    # 修（npm run fix:body）
python3 tools/build_fix_compare.py --ids body --bbox 55,290,145,455   # 局部验收
```

## 八、手部保护：别把"手指的肌肉线"当细丝削掉

### 现象

前臂屈肌群、伸肌群、肱桡肌都会一直延伸到手掌，并分出几束细线指向手指。
这几束中位宽只有 1.75~2.56 单位（栅格下 7~10 px），而红档用的腐蚀半径 r=3
要求结构至少 7 px 宽才活得下来——**它们刚好在刀刃上**。

第一版修缮没做保护，`forearm_flexors` 面积掉了 7.7%、`forearm_extensors` 掉了 9.1%，
手指那几束被整个削平：手部区顶点数从 156 / 70 掉到 29 / 14，肉眼就是"手空了"。

### 做法：区域保护（`PROTECT`）

`body_paths.json` 的 viewBox 固定是 `0 0 200 460`，手的位置是固定的
（y 208~274 的左右两侧外缘，y 上限取 274 是为了不波及从 y≈270 开始的大腿）。
重建时先把这块的原图像素单独存一份，开运算之后再并回去：

```
opened = 开运算(原图, r)
opened = opened ∪ (原图 ∩ 手部区域)      # ImageChops.lighter + multiply
```

手部之外的像素照常削细丝，手部之内一个像素不动。轮廓跟踪、DP、Chaikin 仍然
照跑，所以手指束的锯齿同时被抚平了——比原件还规整一点。

### 效果

| 组 | 面积变化（第一版 → 本版） | 手部区顶点 | 说明 |
|---|---|---|---|
| front `forearm_flexors` | -7.7% → **-0.3%** | 29 → 90 | 手指 5 束回来了 |
| back `forearm_extensors` | -9.1% → **-0.4%** | 14 → 38 | 同上 |
| front `brachioradialis` | -0.9% → **-0.2%** | 10 | 腕部那一小段也保住了 |

全身其余 46 组与第一版**逐字节一致**（只有这 3 组被保护机制影响），
所以这个改动不会牵动已经验收过的形状。

### 试过但否掉的方案

给"体积小的块"单独加保护（免得被腐蚀半径啃变形）。实测反而更糟：
髋内收肌、肩胛提肌这些组的左右两块细丝长度本来就不对称（8.4 / 5.9、0.0 / 6.6），
按块判断会把细丝短的那一块放过去 → **左右腿一边干净一边有毛刺**。
对比实验里"无块级保护"在 16 组上全面不劣于开块级保护，所以最终只保留区域保护。

### 顺带修掉的一个精度坑

`to_d()` 原来按 1 位小数写回。修缮后的点是栅格轮廓重采样出来的，1 位小数
（±0.05 单位）对宽 1~2 单位的窄结构足以让"局部厚度 < 1.5"的判定翻转——
表现为"内存里已经修到 0.0，落盘再读出来却报 10.6"。改成 2 位小数后
诊断值与内存一致（文件 74 KB → 78 KB）。

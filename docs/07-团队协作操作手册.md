# 07 · 团队协作操作手册

> 写给所有肌肉模型项目的成员——包括第一次用 Git 的人。
>
> 目标：你会改代码、会推上去、会和别人协作，而且不会把项目改坏。

---

## 一、先搞懂三个概念（不用背，看懂就行）

### 1. main 是什么？

**main 就是"正式版"**。你现在在 GitHub 上看到的代码，就是 main。它是好的、能跑的、给所有人看的版本。

**规矩：谁都不准直接改 main。** 就像正式出版的书，你不能直接拿笔往上划。

### 2. 分支（branch）是什么？

**分支就是"复印件"**。

你想加一个功能？好，你从 main 复印一份，在复印件上改。改得好，把复印件的内容誊回 main；改砸了，复印件扔掉，main 一个字没动。

**每人都有自己的复印件，互不干扰。**

### 3. PR（Pull Request）是什么？

**PR 就是"我改完了，你帮我看看能不能放进正式版"的申请。**

改完推上去之后，在 GitHub 网页上点一个按钮，对方就能看到"你改了哪几行"。觉得行，点"合并"；觉得不行，让你改。main 里的代码始终是审过的、安全的。

## 二、第一次：把项目拿到自己电脑上

### 情况 A：你是项目 owner（仓库是你的）

你已经有了，不用再 clone。在你的电脑打开终端（Terminal），输入：

```bash
cd ~/Desktop/muscle-model
```

就行了。

### 情况 B：你是协作者（别人拉你进来的）

打开终端，输入：

```bash
cd ~/Desktop
git clone https://github.com/Liushu-sys/muscle-model.git
```

等它跑完，你的桌面上就会多出一个 `muscle-model` 文件夹，里面就是全部代码。

然后进去：

```bash
cd muscle-model
```

## 三、日常改代码的完整流程

### 第 1 步：开分支（复印一份）

每次改东西之前，先开分支。分支名字要让人看懂你在干嘛，比如：

- `fix-hover-bug` —— 修悬停 bug
- `add-relief-page` —— 加缓解动作页
- `update-readme` —— 更新说明文档

终端里输入：

```bash
git checkout -b 你的分支名字
```

**这一行干了什么：** `-b` 就是"新建并切换"，你现在从 main 复印了一份，并且已经在复印件上了。

### 第 2 步：改代码

用你自己的编辑器（VS Code / Cursor / Trae）打开文件，随便改。改的时候随时保存。

### 第 3 步：看看改了什么

改完一堆，先别急着推。先看看自己都动了哪些文件：

```bash
git status
```

终端会列出：
- 红色的 `modified` —— 改过的文件
- 绿色的 `new file` —— 新建的文件
- 红色的 `Untracked files` —— 新文件还没被 Git 管

### 第 4 步：把改动打包（stage）

挑你要提交的文件，一个个加进去：

```bash
git add 文件名
```

比如改了 `README.md` 和 `assets/body_preview.html`：

```bash
git add README.md assets/body_preview.html
```

**注意：** 别用 `git add .`（点号代表全部），除非你确定所有改动都是要提交的。不小心加了临时文件、日志、或者 `node_modules`，会让仓库变脏。

加完再确认一次：

```bash
git status
```

刚才红色的应该变成绿色了。

### 第 5 步：写提交说明（commit）

```bash
git commit -m "你干了什么"
```

提交说明要让别人看懂，比如：

```bash
git commit -m "修复点击肌肉后层级错乱的问题"
```

或者多行说明：

```bash
git commit -m "加诊断结果页" -m "- 支持橘/紫着色
- 点击肌肉弹出 Sheet
- 顶部 AI 摘要可收起"
```

**commit 就是"存盘"**。存在你自己的电脑上，还没推上 GitHub。

### 第 6 步：推上 GitHub

```bash
git push -u origin 你的分支名字
```

`-u` 就是"记住这个对应关系"，下次再推这条分支，直接 `git push` 就行，不用打分支名。

**这一行干了什么：** 把你电脑上的"复印件"推到了 GitHub 服务器上。main 还是原来的样子，你的改动在另一个分支里躺着。

## 四、在 GitHub 网页上开 PR（Pull Request）

推上去之后，打开浏览器，进入仓库页面：

```
https://github.com/Liushu-sys/muscle-model
```

### 第 1 步：找到你的分支

页面顶部会有一条黄色横幅：

> `你的分支名字` had recent pushes less than a minute ago
> **Compare & pull request** ← 点这个

如果没看到横幅，点页面上方的 `Pull requests` 标签 → 绿色按钮 `New pull request`。

### 第 2 步：确认改的内容

页面会显示：
- **base:** `main` ← `compare:` `你的分支名字`
- 下面列出你改的所有文件，绿色是新增的行，红色是删除的行

**仔细看一遍**，确认没有改错文件、没有删掉不该删的东西。

### 第 3 步：写 PR 描述

标题写清楚做了什么，比如：

```
添加诊断结果页：过劳/过弱着色 + 肌肉 Sheet
```

描述里可以写：
- 改了什么
- 为什么改
- 有没有 breaking change（会不会让旧功能坏掉）
- 需要 reviewer 特别看什么

### 第 4 步：创建 PR

点绿色大按钮 `Create pull request`。

### 第 5 步：等 review

创建之后，页面右侧会显示 **Reviewers**。如果你知道该谁审，点齿轮图标 @ 那个人。

**作为 owner（你）审别人的 PR：**

打开 PR 页面 → 点 `Files changed` 标签 → 逐行看改动。觉得哪里有问题，把鼠标悬停在那行，点左边的 `+` 号，写评论：

> "这里颜色值是不是写错了？应该是 `#4198AC`"

全部看完没问题，点右上角绿色按钮 `Review changes` → 选 `Approve` → `Submit review`。

然后点 `Merge pull request` → `Confirm merge`。对方的改动就进 main 了。

**如果发现问题：** 选 `Request changes`，对方会收到通知，改完再推，PR 自动更新，你再看一遍。

## 五、改完之后：同步 main 到本地

别人合并了 PR，main 变了。你本地还是旧的，需要同步。

```bash
git checkout main          # 切回 main
git pull origin main       # 从 GitHub 拉最新的 main
```

然后如果你还要改东西，**重新从最新的 main 开分支**：

```bash
git checkout -b 新分支名字
```

**千万别在旧分支上继续改。** 旧分支是基于旧 main 的，和新 main 可能冲突。

## 六、常用命令速查表

| 你想干什么 | 命令 |
|---|---|
| 看看自己在哪个分支 | `git branch` |
| 切换到 main | `git checkout main` |
| 从 main 开新分支 | `git checkout -b 分支名` |
| 看看改了什么文件 | `git status` |
| 把文件加入提交 | `git add 文件名` |
| 存盘（commit） | `git commit -m "说明"` |
| 推上 GitHub | `git push -u origin 分支名` |
| 拉最新 main | `git pull origin main` |
| 看某个文件改了什么 | `git diff 文件名` |
| 放弃某个文件的改动 | `git checkout -- 文件名` |
| 删除本地分支 | `git branch -d 分支名` |

## 七、常见问题

### Q1：我改到一半，main 上有人合并了新代码，怎么办？

**不要慌。** 先把你的改动存起来：

```bash
git stash
```

然后切回 main 拉最新的：

```bash
git checkout main
git pull origin main
```

再切回你的分支，把最新的 main 合并进来：

```bash
git checkout 你的分支名
git merge main
```

如果提示冲突（conflict），终端会告诉你是哪个文件。打开那个文件，找 `<<<<<<< HEAD` 和 `>>>>>>> main` 这样的标记，手动保留你要的，删掉标记。然后：

```bash
git add 冲突文件名
git commit -m "解决合并冲突"
```

最后把 stash 的改动放出来：

```bash
git stash pop
```

### Q2：我不小心直接改了 main，还没推，怎么救？

```bash
git stash                    # 把改动存起来
git checkout -b 新分支名     # 从 main 开新分支
git stash pop                # 把改动放出来
git add . && git commit -m "xxx"
```

然后 main 上那些没提交的改动就被清掉了，你的改动安全地待在新分支里。

### Q3：我 push 了，但发现改错了，怎么撤回？

如果只是推到了你自己的分支（还没合并到 main）：

```bash
git reset --soft HEAD~1      # 撤销最后一次 commit，改动还留在工作区
git reset --hard HEAD~1      # 彻底丢掉最后一次 commit（慎用）
```

然后强制推（只在自己的分支上用）：

```bash
git push --force origin 你的分支名
```

**如果已经合并到 main 了**，不要 force push main！在 GitHub 上开一个新的 PR，把改错的 revert 掉。

### Q4：`git add` 的时候不小心加了不该加的文件

```bash
git reset HEAD 文件名        # 把文件从 stage 区拿出来，但文件内容不变
```

### Q5：我想看某个人之前改了什么

```bash
git log --author="对方名字" --oneline
```

或者上 GitHub 网页，点 `Insights` → `Contributors`，图形化看谁的提交最多。

## 八、给 muscle-model 项目的特殊约定

### 1. 永远不要改的文件

| 文件 | 为什么 | 动了会怎样 |
|---|---|---|
| `assets/body_preview_original.html` | 它是"最初的预览版"，冻结存档 | 会失去回滚基准 |
| `assets/body_look.png` | 静态样张，对外展示用 | 团队失去参照 |

### 2. 改完原型页必须做的事

如果你改了 `assets/body_preview.html`（主版本原型），改完后顺手更新单文件版：

```bash
cd assets
# 把 mm-engine.js 内联进 HTML（具体命令问 K）
```

单文件版 `BodyMap_单文件版.html` 是发给朋友双击即开的，和主版本要保持一致。

### 3. 改完引擎代码必须做的事

如果你改了 `src/` 里的 TypeScript 源码（诊断引擎、数据表），必须重新打包：

```bash
npx esbuild src/index.ts --bundle --format=esm --outfile=assets/mm-engine.js
```

然后 `git add assets/mm-engine.js` 一起提交。否则预览页用的还是旧引擎。

### 4. 提交前必跑检查

```bash
npm run check
```

这条命令会跑类型检查、单元测试和格式校验。红了就修，绿了再推。

## 九、main 分支保护规则（2026-10-05 起已开启）

本仓库的 main 分支已经由 owner 上锁。下面说清楚**锁了什么、没锁什么**，
大家照做就不会撞墙。

### 锁住的（对所有人，包括协作者）

| 操作 | 结果 |
|---|---|
| 直接 `git push origin main` | GitHub 拒绝，推不上去 |
| 不开 PR、想直接把分支合进 main | 不允许，必须走 Pull Request |
| 自己开 PR 后自己点 Merge | 合并按钮是灰的——PR 必须有 **1 个人批准**，且 GitHub 规定**自己不能批准自己的 PR**，所以批准人只能是 owner（或其他被指定的 reviewer） |
| 对 main 强推（force push）覆盖历史 | 禁止 |
| 删除 main 分支 | 禁止 |

### 没锁的（可以放心做）

- **功能分支随便推**：你自己开的分支（复印件）不锁，`git push origin 你的分支` 正常使用
- **推了就能给 owner 看**：分支一推上 GitHub，即使还没开 PR，owner 在
  `https://github.com/Liushu-sys/muscle-model/branches` 也能看到你的分支和提交；
  开了 PR 之后更能看到逐行红绿 diff
- **没有强制 CI 检查**：目前不要求自动测试通过才能合并（等以后项目有测试了再加）
- **owner 保留应急通道**：仓库主人在紧急情况下可以绕过规则直接操作 main
  （这是 GitHub 给管理员的口子，普通协作者没有），但日常协作 owner 自己也走 PR

### 这套规则下的协作闭环

```
协作者：开分支 → 本地改 → 推自己的分支 → 开 PR
                                      ↓
owner：收到通知 → 看 diff → 批准（Approve）→ 合并进 main
                                      ↓
所有人：git pull origin main 同步最新版，继续下一轮
```

### owner 想查看或调整规则

网页：仓库 **Settings → Branches → Branch protection rules → main(main)**。

命令行查看：

```bash
gh api /repos/Liushu-sys/muscle-model/branches/main/protection
```

> 注：分支保护只防"误操作"，不影响任何人读代码、克隆、在自己分支上试错。

## 十、一句话总结

> **从 main 复印一份 → 在复印件上改 → 推上去 → 开 PR → owner 审过再合并 → 同步 main → 继续下一轮。**

循环往复，项目永远在安全的轨道上前进。

# 09 · 踩坑记录与经验复用

> 项目里真正花时间排掉的坑，都在这。每个坑按
> **现象 → 根因 → 解法 → 预防**四段写。遇到相似问题先搜本文档。

---

## 一、矢量图与点选交互

### 坑 1：点几块肌肉后，肌肉上下层叠关系乱了

**现象**：表层肌肉该盖住深层肌肉，实际显示顺序反过来；多点几块后层级越来越乱。

**根因**：React 版 BodyMap 用"两遍渲染"（未着色的先画、着色的整体抬到最上层）
来保证深层肌肉能被点到。但多选后**所有已着色肌肉整体上浮**，破坏了 SVG 原始的
解剖叠放顺序。

**解法**：回到预览页验证过的策略——**只在点选的瞬间，把被点的那一块
`appendChild` 到父节点末尾（置顶），其余肌肉保持原始 DOM 顺序**。
原始顺序是按解剖层级手工排过的，不要整体重排。

**预防**：
- 不要用"着色集合整体重排"解决深层肌肉点选问题
- 改肌肉叠放逻辑前，先打开 `body_preview_original.html` 对照原版手感

### 坑 2：真实手机/鼠标点肌肉没反应，脚本模拟点击却一切正常

**现象**：自动化测试全绿，真人操作就是点不中。

**根因**：缩放平移逻辑在 `pointerdown` 里**无条件调用了
`setPointerCapture`**，浏览器把后续点击事件强制改投给滚动容器，肌肉 path
永远收不到真实指针事件。脚本 `dispatchEvent(new MouseEvent(...))` 不经过
指针捕获流程，所以测不出来。

**解法**：只有在判定"真的开始拖动/捏合"（位移超过阈值或第二指落下）后才
capture；纯点选不 capture，让事件正常派发给 path。

**预防**：
- 指针事件的 capture/release 必须和"是否进入拖动态"绑定
- 凡是"脚本测着没问题、人点着有问题"，优先怀疑指针捕获、`preventDefault`、
  触摸目标这三类

### 坑 3：肌肉明明能看见，却点不中、取消不掉

**根因**：缩放参考网格的 `<line>` 元素没设 `pointer-events:none`，透明网格线
盖在肌肉上拦截了点击。

**解法**：所有纯装饰/辅助元素（网格、参考线、标签）一律
`pointer-events: none;`，只有真正要交互的元素接收事件。

**预防**：新加任何覆盖在肌肉上层的 SVG 元素，默认就写 `pointer-events:none`，
需要交互再单独打开。

### 坑 4：hover 变色把身体外轮廓也染了

**根因**：CSS 选择器 `.bm-svg path:hover` 同时匹配了 svg 直接子节点的身体
轮廓 path（fill `#FAF6F1`）。

**解法**：选择器限定到肌肉分组内：`.bm-svg g path:hover`。轮廓是 svg 的
直接子节点，肌肉都在 `<g>` 里。

**预防**：写 SVG 交互样式时，交互选择器一律带容器限定，别用裸标签选择器。

### 坑 5：图在页面上完全不显示（高度塌陷为 0）

**根因**：容器用了 `flex-1`，但它的父元素不是 flex 容器，`flex:1` 不生效；
内部又全是 absolute 定位、没有文档流内容撑开，容器高度变 0，被 overflow 裁光。

**解法**：容器改成 `h-full w-full`，并确保父级链路每一层都有确定高度
（flex 列布局用 `min-h-0` 允许子项收缩）。

**预防**：flex 子项的 `flex-1` 生效前提是**父元素 `display:flex`**；
排查"元素不见了"先看 computed height 是不是 0。

## 二、诊断引擎与数据

### 坑 6：17 组肌肉怎么选都诊断不出来（如腹内斜肌、胫骨前肌）

**根因**：两层原因——
1. 这些肌肉不在任何受限模式的 `tight/weak/inferred*` 分组里，模式匹配天然够不到
2. 在模式里的也可能够不到：它的感受词（如"勾脚没力"）触发不了模式词表
   （如"小腿肚紧/脚后跟疼"）

**解法**：加**肌肉级兜底**——对用户选中的每一块肌肉：模式没接住 → 反查
它属于哪个模式分组 → 还查不到，就按 `muscles.ts` 里的常识倾向 `type`
（tight/weak）给结论。兜底项必须在 UI 上用虚线描边 + "推断"标签区分，
不冒充确诊。

**预防**：
- 新增肌肉后，跑一遍"全肌肉点选"穷尽测试，确认每块都能出结论
- 数据层（肌肉表）和规则层（模式表）覆盖范围本来就可能不一致，兜底是
  产品设计的一部分，不是补丁

### 坑 7：摘要里"几处过劳/几处过弱"和图上对不上

**根因**：按 path 计数——三角肌左右两片 path 被算成 2 处；但用户口径是
"按肌肉名称算"。

**解法**：按肌肉 `data-id`（或 muscle id）去重计数，同名左右只算一处。
摘要文案里直接写明口径："同名肌肉左右两侧只计一处"。

**预防**：任何"数几个"的需求，先确认计数单位是 path、肌肉 id、还是
模式 id，三者在本项目里不是一回事。

### 坑 8：某块肌肉的「建议方向」没有具体动作

**根因**：动作按"肌肉 + 状态"严格匹配，但数据可能错位——例如上斜方肌在
肩胛胸壁模式里归 weak（被拉长组），动作库里却只有它 tight 状态的动作。

**解法**：先按状态匹配；该状态无动作时**放宽到该肌肉的全部动作**，保证
用户总能拿到可执行的动作名。

**预防**：动作库扩条目时，尽量给同一块肌肉的两种状态都配动作；匹配逻辑
保持"严格优先、宽松兜底"。

### 坑 9：改了 `src/` 的引擎代码，预览页行为没变

**根因**：`assets/body_preview.html` 动态 import 的是**打包产物**
`assets/mm-engine.js`，不是 `src/` 源码。改源码不重新打包，页面用的还是旧引擎。

**解法**：

```bash
npx esbuild src/index.ts --bundle --format=esm --outfile=assets/mm-engine.js
```

然后把 `mm-engine.js` 一起提交。

**预防**：提交涉及引擎/数据改动时，检查 `mm-engine.js` 是否在改动文件列表里。

## 三、浏览器环境与分发

### 坑 10：双击打开 HTML，点肌肉没反应（file:// 协议）

**根因**：浏览器安全策略禁止 `file://` 页面加载 ES module
（`import('./mm-engine.js')`），脚本直接挂掉。

**解法（按场景选）**：
- **自己开发预览**：走 HTTP 服务
  `python3 -m http.server 8765 --directory assets`，访问
  `http://localhost:8765/body_preview.html`
- **发给不懂技术的朋友双击即开**：用 `BodyMap_单文件版.html`——构建时把
  引擎的 `export {...}` 改成 `window.MM_ENGINE = {...}` 内联进 HTML，
  零网络请求，file:// 也能跑

**预防**：主版本（依赖外部 js）和单文件版（引擎内联）是两个分发通道，
改完主版本记得重新合并生成单文件版。

### 坑 11：浏览器/自动化测试读到的是旧页面

**根因**：本地静态服务和浏览器都有缓存。

**解法**：URL 加版本参数破缓存 `body_preview.html?v=15`；真人验证用
**Cmd+Shift+R** 强刷。

**预防**：每次改完让别人验证，直接把带新版本号的链接发过去，别只说"刷新试试"。

## 四、构建与依赖（React 备用版 app/）

### 坑 12：Vite 构建报 react 是空壳 / Invalid hook call

**根因**：muscle-model 库把 react 声明为可选 peer dependency，Vite 解析
上层文件里的 react 导入时套了空实现，导致项目里存在两份 react。

**解法**：`app/vite.config.ts` 里加 alias 强制所有 react 导入指向
app 自己的 node_modules，并 dedupe：

```ts
{ find: /^react(\/.*)?$/, replacement: resolve('node_modules/react') + '$1' }
// resolve.dedupe: ['react', 'react-dom']
```

### 坑 13：TS 6 报 `baseUrl` 弃用

**解法**：去掉 tsconfig 里的 `baseUrl`，`paths` 直接用相对于 tsconfig
的路径（如 `"@model/*": ["../src/*"]`）。

## 五、Git / GitHub 协作

### 坑 14：`fatal: Unable to create '.git/index.lock'`

**根因**：上一次 git 进程异常退出留下锁文件，或有别的 git 进程在跑。

**解法**：先确认没有 git/IDE 正在执行 git 操作，然后：

```bash
rm -f .git/index.lock
# 远程引用锁同理：
rm -f .git/refs/remotes/origin/main.lock
```

### 坑 15：协作邀请差点发错人——同名账号极多

**现象**：GitHub 上显示名为 "Ming Jing" 的账号至少 3 个，用户名相近的几十个。

**解法/规矩**：
- **发邀请前必须核对对方的 GitHub 主页链接**（让对方本人发你），不能只凭
  显示名或猜测的用户名
- 发错后立即撤回：
  `gh api --method DELETE /repos/<owner>/<repo>/invitations/<邀请id>`
- 发邀请命令：
  `gh api --method PUT /repos/<owner>/<repo>/collaborators/<用户名> -f permission=push`

### 坑 16：IDE 的 Markdown 格式化插件"悄悄改文档"

**现象**：提交后文档又显示有改动；diff 里 `---` 变 `***`、`~` 被加转义，
甚至把"轮廓修缮说明"吃掉一个字变成"轮廓修缮说"。

**解法**：这类无意义且可能损坏内容的改动不要提交，直接恢复：

```bash
git checkout -- 文件名
```

**预防**：IDE 弹出"是否格式化"时对 docs 下的手写文档点拒绝；需要统一格式
时再单独做一次"纯格式化提交"，不和内容改动混在一起。

### 坑 17：以为口头约定"别推 main"就够了

**根因**：write 权限的协作者默认能直推 main、也能自批自合 PR，文档约定
没有强制力。

**解法**：给 main 开分支保护——必须走 PR + 至少 1 人批准（自己不能批自己），
禁强推、禁删除。详见 `07-团队协作操作手册.md` 第九节。

## 六、验证方法论

1. **穷尽测试 > 抽样测试**：诊断覆盖这类问题，写个脚本把全部 47 组肌肉
   逐个点一遍，比随手点 5 块靠谱得多（坑 6 就是这样暴露的）
2. **真人手感 > 自动化脚本**：指针捕获、触摸目标、hover 这类问题脚本测不出
   （坑 2），改完交互一定自己上手点一遍
3. **改动后三件套**：`npm run check`（类型/测试）→ 浏览器实测 → 控制台
   确认零报错
4. **对照基准**：任何点选/层级的手感争议，先打开冻结版
   `body_preview_original.html` 对比，它是"正确手感"的基准线

## 七、可复用 Skill 索引（跨项目模板）

以下 skill 存放在 `~/trae-templates/skills/`，是跨项目通用的流程模板。
遇到对应场景时，先让 AI 去读对应路径下的 SKILL.md，再按里面的流程执行。

| 遇到什么情况 | 去调用哪个 Skill | 路径 |
|---|---|---|
| 复杂改动：多文件修改、新功能、需求描述模糊（"感觉不对/优化一下"） | **app-change-flow**：听懂→拆解→施工→验收 四阶段流程 | `~/trae-templates/skills/app-change-flow/SKILL.md` |
| 要把项目推/传/备份到 GitHub，或新建仓库 | **github-publish**：gh CLI 建仓、提交、推送、登录排障 | `~/trae-templates/skills/github-publish/SKILL.md` |
| 要把网页做成手机能打开的公网链接、部署到服务器、分享给别人、移动端自适应 | **web-to-mobile-deploy**：阿里云服务器信息、scp 部署、防缓存、viewport/100dvh/safe-area、悬浮 UI、iOS 状态栏融合、双视口验证 | `~/trae-templates/skills/web-to-mobile-deploy/SKILL.md` |

**注意**：`~/trae-templates/` 在用户目录下，不属于任何项目、不被 git 跟踪，
改它不影响项目代码；新项目要复用时可直接复制到项目内或引用路径。
